# IPE-F4414: an author-asserted foreign call (Rust.Ffi.call) was refused

Your `Rust.Ffi.call` site has the right shape, but the assertion itself
was refused before any foreign code was generated. This page explains
each refusal class and its fix.

## The target crate is not installed

The path's first segment names the Rust crate, and that crate must
already be a declared dependency (`ipe rust add some_crate`).
`Rust.Ffi.call` can never bypass the admission pipeline — the trust
prompt, the sandboxed build, the capability disclosure. An asserted
call into an undeclared crate is refused here, not fetched.

## The asserted signature uses a type outside the closed carrier set

An asserted signature may only name types the boundary already admits:
the scalar carriers — `Int` (`i64`), `Float` (`f64`), `Bool`, `Char`,
`String`, `Bytes` (`Vec<u8>`) — plus `()` as the sole parameter of a
zero-argument target, opaque handle types the target crate's inspected
interface already declares, and a result of exactly `Result Error <T>`:

```ipe ipe:skip illustrates an asserted-call signature shape, not a runnable program here
import Rust.Ffi
import Rust.Semver exposing (Version)

reparse : Version -> Result Error Version
reparse =
    Rust.Ffi.call "semver::reparse"
```

Type variables, tuples, lists, records, functions, and nominals from
*other* crates are refused: an assertion cannot conjure a new type
mapping or forge another crate's handle.

## The assertion disagrees with the crate's inspected signature

When the target function *is* in the crate's inspected interface, the
assertion is checked against the inspected signature at compile time.
The check is **exact-carrier**: each asserted type must match the Rust
type precisely — `Int` is exactly `i64`, never `u32` or `usize`. There
is no silent widening, narrowing, or clamping inside an asserted shim;
a signature that would need one is refused, and the diagnostic names
the Rust type the target actually declares.

So for a Rust function `fn count() -> u32`, this assertion is refused
(`Int` is `i64`, and `u32 -> i64` would need a conversion the asserted
shim refuses to hide):

```ipe ipe:skip illustrates a refused asserted-call signature, not a runnable program here
count : () -> Result Error Int
count =
    Rust.Ffi.call "some_crate::count"
```

If the target's types have no exact Ipê carrier, use the inspected
import instead: the inspected path carries the documented saturating
conversions, disclosed as such.

## The target's shape is outside the asserted-call subset

Asserted calls cover plain synchronous functions returning a bare
carrier value. An `async fn`, a `Result`/`Option`-returning function, a
generic function, or an `unsafe fn` is refused — the inspected import
covers most of these shapes with full checking.

## Conflicting assertions

Two definitions asserting *different* signatures for the *same* Rust
function cannot both be right, so the build is refused rather than
silently trusting one of them. Make the assertions identical, or keep a
single asserted definition and import it where needed:

```ipe ipe:skip illustrates a single asserted definition, not a runnable program here
frobnicate : Int -> Result Error Int
frobnicate =
    Rust.Ffi.call "some_crate::frobnicate"
```

## What an accepted assertion still cannot break

Even an accepted assertion is not taken on faith:

- if the function was *not* in the inspected interface, the generated
  shim carries your asserted types verbatim and **rustc is the checker
  of record** — a wrong assertion fails the emitted build inside the
  shim, attributed to your assertion, never undefined behavior;
- every asserted shim runs inside the panic boundary: a panicking
  foreign call becomes a typed `Err`, never an escaping unwind;
- using the escape at all flips the `ffi-raw` capability on the
  program: it is surfaced in capability listings and gated by package
  admission, so a package using the escape is honest about it by
  construction.
