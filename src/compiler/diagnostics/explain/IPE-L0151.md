# IPE-L0151: `Secret.fromString` must be applied directly to its argument

`Secret.fromString` is the single seal that turns a runtime `String` into a
typed `Secret`. That seal is guarded: a **quoted string literal** as its
argument is a credential committed to source, and the compiler refuses it
(IPE-L0150). But that guard reads the **argument of the call** — it can only
fire when `Secret.fromString` is applied right there, with its argument in view.

This error means `Secret.fromString` was used **without being applied** — passed
as a value, bound to a name, or otherwise left point-free. When the seal is
un-applied, its argument is supplied somewhere else, out of the guard's sight,
so a committed credential could slip past it. To keep the guard honest,
`Secret.fromString` is legal **only as a direct one-argument call**.

```ipe ipe:skip the point-free `Secret.fromString` shape IPE-L0151 flags; shown without running the checker
import Ipe.List as List
import Ipe.Secret

-- Reject: `Secret.fromString` is passed as a value, so the literal `"sk_live_…"`
-- is applied later, out of the seal guard's sight.
sealed : List Secret
sealed =
    List.map Secret.fromString [ "sk_live_51H8xY2abc..." ]
```

```ipe ipe:skip the point-free `Secret.fromString` shape IPE-L0151 flags; shown without running the checker
import Ipe.Secret

-- Reject: binding the seal to a name is the same escape — `seal` carries the
-- un-applied `Secret.fromString`, and the literal is applied through the alias.
sealed : Secret
sealed =
    let seal = Secret.fromString
    in seal "sk_live_51H8xY2abc..."
```

## How to fix it

Apply `Secret.fromString` directly to its argument, so the seal guard sees that
argument. A runtime `String` is accepted; only a source-text literal is refused:

```ipe ipe:skip the direct-application fix; shown without running the checker
import Ipe.List as List
import Ipe.Secret
import Ipe.System as System

-- Accept: the seal is applied to a runtime String read from the environment.
key : Secret
key =
    Secret.fromString (System.getenvOr "STRIPE_API_KEY" "")

-- Accept: to seal each String in a list, apply the seal inside a lambda — it is
-- fully applied to the lambda's own parameter, so the guard still fires.
sealAll : List String -> List Secret
sealAll raws =
    List.map (\raw -> Secret.fromString raw) raws
```

## Why the compiler refuses this

Under Ipê's first principle — Security — a secret must give an attacker no
foothold, and the safe outcome is the only reachable one (fail closed). The
committed-literal ban is only as strong as its coverage: if `Secret.fromString`
could be passed around un-applied, a credential could reach a `Secret` on a path
the argument guard never inspects. Requiring the seal to be fully applied makes
the guard **structural** — every `String` that becomes a `Secret` does so at a
call site whose argument is checked. A literal smuggled through a data structure
and a lambda (or rebuilt from characters) is deliberate obfuscation that no
source-literal ban can stop; this rule closes the accidental paths — passing the
seal as a value and aliasing it — not that one.
