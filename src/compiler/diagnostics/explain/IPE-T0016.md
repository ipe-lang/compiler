# IPE-T0016: async carrier (`Task`/`Cmd`/`Sub`) applied to the wrong number of type arguments

`Task` is the built-in effect type. Its user-facing form takes
**exactly two** type arguments — an error channel and a success type:

```ipe
import Ipe.Task as Task

type alias Config =
    { timeout : Int }

readConfig : String -> Task Error Config
readConfig path =
    readConfig path
```

The error channel is always `Error` (that is checked separately by IPE-T0001),
and the success type is whatever the task produces. Applying `Task` to any other
number of type arguments is not a valid type: a bare `Task` (zero arguments)
names the constructor without saying what it produces, and a three-or-more
argument application like `Task Error Int Bool` has no meaning — `Task` is not
that kind of type.

## Wrong

```ipe ipe:error
import Ipe.Task as Task

-- error: `Task` applied to 3 type arguments
doThing : String -> Task Error Int Bool
doThing s =
    Task.succeed 42
```

```ipe ipe:error
import Ipe.Task as Task

-- error: `Task` applied to 0 type arguments — no success type
doThing : Task
doThing =
    Task.succeed 42
```

## Right

Give `Task` its two arguments: the fixed `Error` channel and the success type.

```ipe
import Ipe.Task as Task

doThing : String -> Task Error Int
doThing s =
    Task.succeed 42
```

The same rule applies wherever a `Task` type appears, including inside a
constructor payload:

```ipe
type Job = Job (Task Error Int)
```

Here `Task Error Int` is well-formed; `Job (Task Error Int Bool)` would be
reported with this same code.

## Why this is caught here

The compiler validates the argument count only for type *aliases*. `Task` is
a built-in type constructor, not an alias, so a mis-applied `Task` slips past
that check and reaches type checking — where this diagnostic names the
argument count it actually found, rather than the compiler falling over with an
internal error.

## `Cmd` and `Sub`

The same rule covers the two other async carriers, `Cmd` and `Sub` — but they
take **exactly one** message type, not two:

```ipe ipe:error
type Model = Model

-- error: `Cmd` applied to 2 type arguments
subscriptions : Model -> Cmd Int Bool
subscriptions model =
    subscriptions model
```

Give them their single message type:

```ipe
type Model = Model

type Msg = Tick

subscriptions : Model -> Cmd Msg
subscriptions model =
    subscriptions model
```
