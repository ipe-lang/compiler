# IPE-L0143: caller field type does not match the field type required by the callee

A function whose parameter is annotated `any` reads one or more fields from that
parameter. Ipê's backend erases the `any` to a **row-generic** bounded by one
field-witness trait per field read, so the required field type is baked into the
emitted Rust bound. A caller whose record has that field at a **different** type
would produce Rust that fails to compile with E0271, even though the type-checker
accepted the call (because `any` intentionally severs the normal check that a
caller's argument type matches the callee's parameter type). This diagnostic
catches that mismatch at Ipê time.

```ipe ipe:skip the field-type mismatch IPE-L0143 flags; shown without running the checker
getName : any -> String
getName p =
    String.append p.name "!"

-- wrong: { name = True } provides Bool where String is required
result = getName { name = True }
```

The function `getName` reads `p.name` and its body constrains that field to
`String`. The caller passes `{ name = True }`, whose `name` field is `Bool`.
Ipê rejects this call here rather than emitting Rust that `cargo` cannot build.

## How to fix

**Pass a record with the correct field type.** If the field must be `String`,
supply a `String` value:

```ipe
getName : any -> String
getName p =
    String.append p.name "!"

result = getName { name = "Ada" }
```

**Or annotate the callee's parameter with a closed record type.** A closed record
type (`{ name : String }`) lets the type-checker enforce the field constraint at
every call site before lowering:

```ipe
getName : { name : String } -> String
getName p =
    String.append p.name "!"

-- now a type error at check time, not a lowering rejection:
result = getName { name = True }
```

**Or use a row-polymorphic annotation.** If you want to accept any record that
carries at least a `name : String` field, write an explicit row annotation:

```ipe
getName : { r | name : String } -> String
getName p =
    p.name
```

## Why this happens

A wildcard `any` severs the normal check that a caller's argument type matches
the callee's parameter type: the type-checker accepts a call `f { name = True }`
where `f : any -> String` because `any` is a one-shot placeholder that the caller
fills, not a type variable that propagates field constraints back to the call
site.

When `f`'s body reads `p.name`, the backend lowers `p` to a Rust generic bounded
by `IpeHasName<Name = String>`. That bound says "`p.name` returns `String`." A
caller passing `{ name = True }` produces a Rust struct where
`<RecName as IpeHasName>::Name = Bool`, which does not satisfy `Name = String` —
E0271. Ipê catches this at lowering time so you see a clear message, not a
`cargo` build failure.

## Glossary

- **wildcard `any`** — a placeholder for one concrete type the compiler determines
  from the surrounding context. Unlike a named type variable, it is not left open
  for callers to instantiate.
- **row-generic** — a Rust generic bounded by one synthesised witness trait per
  required field, monomorphised by `rustc` per record shape.
- **field-witness trait** — a synthesised `IpeHas<Field><Name = T>` trait the
  backend generates; its associated type `Name` carries the required field type.
- **E0271** — a Rust error: an associated-type equality bound is not satisfied.
  From Latin *associatus* ("united, joined"): the associated type does not join
  with the required concrete type.
