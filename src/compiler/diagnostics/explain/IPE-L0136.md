# IPE-L0136: `main` is not a runnable program entry

Every Ipê program has one door in: a top-level definition called `main`. When you
run the program, that is the single thing that happens — so `main` has to *be*
something that happens. In Ipê, "something that happens" has a type: `Task Error ()`.

A `Task` is a described effect: printing a line, serving a page, drawing a screen.
`main : Task Error ()` says "this program's one job is this effect". Give `main`
any other type — an `Int`, a `String`, a function — and there is no effect to run.
The program has a value where it needs an action.

## What went wrong

Your `main` has a type that is not a `Task Error ()`, and is not one of the app
entries that produce one:

```ipe ipe:error
module Main exposing (main)

main : Int
main = 42
```

`42` is a number, not an effect. Running this program would mean... doing what with
`42`? There is nothing to do. So the compiler stops here, at `ipe` time, rather than
building a program that could not run.

## How to fix it

**Print it, or do something with it.** If you meant to show the value, turn it into
an effect:

```ipe ipe:skip the properly-typed main that compiles; shown without running the checker
module Main exposing (main)

main : Task Error ()
main =
    Io.println (String.fromInt 42)
```

Now `main` builds a `Task` that prints `42` when the program runs.

**Run any task you built.** A script's `main` is whatever effect it performs — a
chain of `Io`, `Http`, `File`, `Time` calls sequenced with `Task.andThen`:

```ipe
import Ipe.Io as Io
import Ipe.Task as Task

main : Task Error ()
main =
    Io.println "starting"
        |> Task.andThen (\_ -> Io.println "done")
```

**Start an app.** A TEA program's `main` is an app entry — `Web.tea`,
`Tui.tea`, `Cli.tea`, or `WebView.app`. Each of these is
*itself* a `Task Error ()`, so an app `main` needs no annotation:

```ipe ipe:skip a fragment; init, update, view, and subscriptions are assumed from context
main =
    Web.tea
        { init = init
        , update = update
        , view = view
        , subscriptions = subscriptions
        }
```

## Why the rule exists

When Ipê builds your program it wraps `main` in the one place an effect is actually
run. That run site can only run a `Task` — it has nothing to do with an `Int` or a
function. If `main` were allowed to be any type, the program would be handed a value
where it expected an action, and it could not be built. Requiring `main` to be a
`Task Error ()` up front means a program the compiler accepts is a program that can
run: the mismatch is caught here, in a message you can act on, instead of surfacing
later as an inscrutable build error.

For the same reason `main` takes no arguments: the run site calls it with none. A
`main` that expects a parameter (even one that then returns a `Task`) has nothing to
supply it, so it is a function, not a runnable entry. Drop the parameter and build
whatever it needed inside `main`.

## Glossary

- **entry** — the single starting point of a program, the one definition the
  runtime calls. Here it is always `main`. From Old French *entrée*, "a going in".
- **`Task`** — Ipê's type for a *described, not-yet-run* effect. Holding a `Task` is
  holding a plan; running it carries the plan out.
- **effect** — an observable interaction with the outside world: printing, reading,
  serving, drawing. From Latin *efficere*, "to bring about".
- **app entry** — `Web.tea` / `Tui.tea` / `Cli.tea` /
  `WebView.app`: a builder that takes your `init`/`update`/`view` and produces the
  `Task Error ()` that runs the whole interactive loop.
- **`Task Error ()`** — a task that, when run, performs an effect, may fail with an
  `Error`, and yields nothing useful (`()`). The `()` is the empty tuple, "no
  interesting result".
