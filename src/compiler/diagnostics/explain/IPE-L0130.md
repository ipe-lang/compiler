# IPE-L0130: a foreign opaque FFI handle is used more than once

A value whose type is a foreign opaque handle bound from an FFI crate (a type
declared by a `Rust.*` interface module — e.g. `bevy_ecs::World`) was used more
than once in a value-CONSUMING (non-call) position.

An FFI handle IS the real foreign Rust type. Ipe is a value-semantics language,
so reusing a binding normally makes the backend insert a `.clone()`. But a
foreign Rust type need not implement `Clone` — `bevy_ecs::World` does not — so
that inserted `.clone()` may not compile. Rather than emit Rust that `cargo`
rejects after `ipe dev build` already reported success, the compiler fails closed
here.

A by-borrow reader (`&self` / `&mut self`) threads its receiver back beside the
result, so it binds as `World -> Result Error (T, World)` and hands the handle
on. Reusing the ORIGINAL binding after such a call — instead of the returned
handle — is still a non-linear use and fails closed:

```ipe ipe:skip
-- before (IPE-L0130 — `world` is consumed twice, ignoring the threaded handle)
readTwice world =
    let
        a = World.entityCount world
        b = World.changeTick world
    in
        Result.map2 (\x y -> x + y) a b
```

## How to fix

**Thread the handle linearly.** A by-borrow reader returns `(value, handle)`;
destructure it and feed the RETURNED handle to the next call, never the spent
original:

```ipe ipe:skip
-- after (each read hands the world on; the next call uses the returned handle)
readTwice world =
    World.entityCount world
        |> Result.andThen
            (\( count, w1 ) ->
                World.changeTick w1
                    |> Result.map (\( tick, _ ) -> count + tick)
            )
```

**Re-create the handle for each independent consumer** when construction is
cheap and the two uses are genuinely independent:

```ipe ipe:skip
-- after (two independent handles, each used once)
twoReads =
    Result.map2
        (\a b -> a + b)
        (Result.andThen World.entityCount (World.new ()))
        (Result.andThen World.changeTick (World.new ()))
```

## Why this happens

A shim-free FFI binding maps an Ipe opaque type onto the real foreign Rust
type. Whether that type is `Clone` is the foreign crate's decision, not Ipe's,
so the backend cannot safely insert a duplicating `.clone()` for a non-linear
use. This is a conservative gate: it will be relaxed once FFI receivers are
threaded by borrow (`&self` / `&mut self`), so a reader binds as
`World -> Result Error (T, World)` and the handle flows on without a clone.

## Types affected

- Any opaque type declared by a `Rust.*` FFI interface module whose foreign
  Rust type is not `Clone`
- The same handle held inside a `Maybe` / `Result` / tuple / user-union payload
