# IPE-T0014: this type does not support the required operations

A generic function whose body uses one of its type variables with an
operation that only *some* types support was called at a type that does not
support it. Adding (`+ - *`) needs a **Number**; ordering (`< > <= >=`)
needs a **Comparable**; equality (`== /=`) needs an **Equatable**;
`{{expr}}` interpolation and a `Log.*With` attribute need an **interpolable
scalar**; `Debug.log` and `errorToString` need a value with a **text
rendering** (anything but a function); a SQL parameter needs one of `Int`,
`Float`, `String`, `Bool` or `SqlValue`; and a higher-order kernel's callback
must return a **plain value**, not a function. Calling
such a function at, say, `Bool` asks the generated code to add two `Bool`s,
and calling an equality-using function at a *function* type asks it to
compare two functions — neither has any meaning.

## Explanation

A bare type variable means "any type at all": the body only passes the
value through, so the function works for every caller. The instant the body
performs an operation, the variable is no longer "any type" — it must be
one of the types that provides that operation. The compiler records the
obligation on the variable and, at each call, checks the type the caller
chose against it.

`Number` is satisfied by `Int` and `Float`. `Comparable` is satisfied by
the scalar primitives `Int`, `Float`, `Char`, `String`, and `Bool`. A
generic function orders its own type variable only at `Int`, `Float`,
`Char`, or `Bool`: `String` is comparable, but ordering it through a type
variable is refused, so give that value the type `String` in the
function's signature instead. `Equatable` is
the widest of the three — every type *except* a function: the primitives,
tuples, records, and custom types can all be compared for equality, but a
function cannot. A type outside the relevant set — for arithmetic and
ordering, anything other than the listed primitives; for equality, a
function (or a tuple / record holding one) — or a type variable that is
itself still generic, does not satisfy the obligation, so the call is
rejected here rather than producing code that fails to build.

## Examples

`double` adds its argument to itself, so its variable must be a `Number`.
Calling it at `Int` or `Float` is fine:

```ipe
import Ipe.Io as Io
import Ipe.String as String

double : a -> a
double x = x + x

main : Task Error ()
main =
    Io.println (String.fromInt (double 21))   -- 42
```

Calling it at `Bool` is the error — `Bool` is not a `Number`:

```ipe ipe:error
double : a -> a
double x = x + x

check = double (1 == 1)   -- Bool does not support +
```

`maxOf` orders its arguments, so its variable must be `Comparable`. `Char`
is comparable, so this is fine; a tuple is not, so it is rejected:

```ipe
import Ipe.Io as Io
import Ipe.String as String

maxOf : a -> a -> a
maxOf a b = if a > b then a else b

main : Task Error ()
main =
    Io.println (String.fromChar (maxOf 'a' 'z'))   -- z
```

`eq2` compares its arguments for equality, so its variable must be
`Equatable`. Any primitive, tuple, record, or custom type works; only a
function is rejected:

```ipe ipe:error
eq2 : a -> a -> Bool
eq2 p q = p == q

apply : (Int -> Int) -> Int -> Int
apply f x = f x

check = eq2 apply apply   -- error: a function is not Equatable
```

The fix is to call the function at a type that provides the operation —
typically `Int` or `Float` for arithmetic, any scalar primitive for
comparison, any non-function type for equality, and a `String` / `Int` /
`Float` / `Bool` / `Char` for interpolation.

### The interpolable-scalar obligation

`{{expr}}` interpolation and the attribute list of `Log.infoWith` /
`debugWith` / `warnWith` / `errorWith` accept exactly five types: `String`,
`Int`, `Float`, `Bool` and `Char`. Each renders as its `String.from*`
conversion. Anything else — a record, a custom type, a `List`, a `Maybe`, a
tuple, a `Dict`, or an opaque runtime value such as a `Request` or a
`Secret` — is refused, directly or through a generic function that
interpolates its argument. There is no fallback rendering, so a secret or an
unordered map can never slip into text by accident.

```ipe ipe:error
import Ipe.Io as Io

type alias Point =
    { x : Int, y : Int }

main : Task Error ()
main =
    let
        p = { x = 1, y = 2 }
    in
    Io.println """at {{p}}"""   -- error: a record is not an interpolable scalar
```

The fix is to interpolate the fields, or convert the value first
(`String.fromInt`, `Error.toString`, `Secret.redacted`):

```ipe
import Ipe.Io as Io

main : Task Error ()
main =
    let
        p = { x = 1, y = 2 }
    in
    Io.println """at {{p.x}},{{p.y}}"""   -- at 1,2
```

### The callback-result obligation

A pure higher-order kernel applies its callback to an exact number of
arguments: `List.map` and `Maybe.map` to one, `List.foldl` and `map2` to two,
and so on for `Dict.map`, `String.foldl`, `mapError`, `andMap` and their
siblings. The callback's final result must be a plain value, not a function.
A callback with arguments left over after those applications — a
two-argument function handed to `List.map`, a three-argument function handed
to `map2`, a curried payload flowing through `andMap` — would leave a
function where the kernel produces a value, and that shape has no sound
lowering. The label names the kernel and points at the callback: "`List.map`
needs its callback to return a plain value, not a function; this callback
returns `number -> number`", with a second label on the `List.map` reference.
When the refusal cannot tie the duty to one kernel reference in the same
module (an annotated forwarder, or a helper imported from another module), it
states the duty alone: "this callback result must be a plain value, not a
function; this is `Int -> Int`".

```ipe ipe:error
import Ipe.Io as Io
import Ipe.List as List
import Ipe.String as String

add a b =
    a + b

main : Task Error ()
main =
    List.map add [ 1, 2, 3 ]   -- error: `add`'s result is `number -> number`
        |> List.length
        |> String.fromInt
        |> Io.println
```

The refusal is the same whether the kernel is called directly or reached
through a `let`-binding, a bare alias, a higher-order argument, a record
field, or an annotated forwarder:

```ipe ipe:error
import Ipe.Maybe as Maybe

am1 : Maybe a -> Maybe (a -> b) -> Maybe b
am1 x f =
    Maybe.andMap x f

am2 : Maybe a -> Maybe (a -> b) -> Maybe b
am2 x f =
    am1 x f   -- error: `b` has escaped into `am2`'s own annotation
```

Apply the missing argument inside the callback instead
(`List.map (\x -> add x 1) xs`), or use the kernel whose callback takes every
argument (`List.map2 add xs ys`). A fold whose accumulator is itself a
function is refused on the same grounds: build the function outside the
fold, or fold over data and apply it afterwards. `Task`, `Cmd`, `Sub`, and
`Decoder` kernels box their callbacks and carry no such restriction.

The check is conservative where the result type escapes into another
binding's generic variable, as `am2` above shows: a forwarder of a forwarder
is refused at the inner reference even when every eventual payload would be
safe. Call the kernel, or one annotated wrapper of it, at the use site, or
pin the intermediate forwarder to concrete types.

An exact-arity callback is fine, including through a `let`-bound alias:

```ipe
import Ipe.Io as Io
import Ipe.Maybe as Maybe
import Ipe.String as String

inc n =
    n + 1

main : Task Error ()
main =
    let wrapped = Just 41 |> Maybe.andMap in
    wrapped (Just inc)
        |> Maybe.withDefault 0
        |> String.fromInt
        |> Io.println   -- 42
```

## Comparison

It is like a recipe that says "stir until smooth". You can hand the cook
batter or sauce, but not a brick: the instruction only makes sense for
things that can be stirred. The signature `a` looked like "anything", but
the step inside narrowed it to "anything stirrable".

## Names and origins

A **super-type** here is a named family of types sharing an operation —
`Number`, `Comparable`, `Equatable`, interpolable scalar — in the lineage of Elm's constrained
type variables (`number`, `comparable`), which Ipe inherits. The word
*super* is Latin for "above": the family sits above its members, gathering
the types that share a capability. *Equatable* is built from Latin
*aequare*, "to make equal", with the English suffix *-able*, "able to be":
a type able to be tested for equality. A **bound** is the constraint
attached to a generic parameter; *bound* descends from Old French *bonde*,
"a limit", because it limits which types the parameter may take.
