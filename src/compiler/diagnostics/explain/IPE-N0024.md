# IPE-N0024: ambiguous import

Two or more `import` statements bring the same unqualified name into scope. I cannot determine which binding to use at a call site, so I reject the program.

Two modules both expose a value named `render`:

```ipe ipe:skip
module Main exposing (main)
import Html exposing (render)
import Xml exposing (render)

main = println (render someData)
```

Both `Html.render` and `Xml.render` are now in scope as plain `render`. When you write `render someData`, I do not know which one you mean.

To fix this, qualify at least one of the imports so the names no longer collide:

```ipe ipe:skip
module Main exposing (main)
import Html as Html
import Xml exposing (render)

main = println (Html.render someHtml)
```

Or give one import an alias and avoid the `exposing` overlap:

```ipe ipe:skip
module Main exposing (main)
import Html
import Xml as X

main =
    let htmlOut = Html.render someHtml
        xmlOut  = X.render someXml
    in println (htmlOut ++ xmlOut)
```

The same rule applies to types and constructors. If two modules expose a type `Error` unqualified, the error is the same. Qualify one of them to resolve the ambiguity.

An open import (`exposing (..)`) of a standard-library module brings in every name it exposes, so two open imports can share a name without any conflict. The error appears only where you write that name bare:

```ipe ipe:skip
module Main exposing (main)
import Ipe.Io as Io
import Ipe.Parser as Parser exposing (..)
import Ipe.Ui.Transition exposing (..)

f : Step -> Int
f _ = 0

main = Io.println "ok"
```

Both modules declare their own `Step`, so the bare `Step` in the annotation is ambiguous. Without that bare use, the program compiles. A qualified use such as `Parser.Step` or `Parser.Done` always resolves, and a name you define locally or import by an explicit list (`exposing (Step)`) takes precedence over an open import. Two explicit lists that name the same thing still conflict at the import itself.

A local declaration that clashes with an EXPLICIT import of the same name (rather than an open one) is a different case: it is refused eagerly, right at the declaration, under IPE-N0010, IPE-N0011, or IPE-N0012 depending on the namespace — never deferred to a bare use the way two open imports are here.
