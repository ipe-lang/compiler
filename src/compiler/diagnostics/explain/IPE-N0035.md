# IPE-N0035: Cmd / Sub imported from a different shape than the app's

Every TEA app has a **shape** — `Web`, `WebView`, or `Terminal` — fixed by the entry kernel its `main` calls (`Web.tea`, `WebView.app`, `Tui.tea`, or `Cli.tea`). `Cmd` and `Sub` — the commands an `update` returns and the subscriptions a `subscriptions` declares — are **shape-specific**, so each shape re-exports them under its own module:

```text
Web app       -> Ipe.Tea.Web.Cmd     / Ipe.Tea.Web.Sub
WebView app   -> Ipe.Tea.WebView.Cmd / Ipe.Tea.WebView.Sub
Tui app       -> Ipe.Tea.Tui.Cmd     / Ipe.Tea.Tui.Sub
Cli app       -> Ipe.Tea.Cli.Cmd     / Ipe.Tea.Cli.Sub
```

`Tui` and `Cli` are two separate shapes here, even though both draw to a terminal: each `Sub` module owns that shape's input subscription (`Ipe.Tea.Tui.Sub.onKey` reads keys, `Ipe.Tea.Cli.Sub.onLine` reads lines), and a `Cli` app has no key stream, just as a `Tui` app has no line stream. Only `Ipe.Tea.Terminal.Cmd` / `Ipe.Tea.Terminal.Sub`, which carry no input subscription, are shared by both.

Reaching for another shape's `Cmd` or `Sub` is rejected here, at compile time. This `Tui` app imports the `Web` shape's `Cmd`:

```ipe ipe:error
-- rejected: Ipe.Tea.Web.Cmd inside a Tui app
module Main exposing (main)

import Ipe.Tea.Tui as Tui
import Ipe.Tea.Web.Cmd as Cmd

main =
    Tui.tea { init = init, update = update, view = view, subscriptions = subs }
```

## How to fix

**Import `Cmd` / `Sub` from your app's own shape.** The app above is a `Tui` app (its `main` calls `Tui.tea`), so it reaches `Cmd` through `Ipe.Tea.Tui.Cmd`:

```ipe ipe:error
-- accepted: the Tui shape's own Cmd
module Main exposing (main)

import Ipe.Tea.Tui as Tui
import Ipe.Tea.Tui.Cmd as Cmd

main =
    Tui.tea { init = init, update = update, view = view, subscriptions = subs }
```

The alias you bind (`as Cmd`) is unchanged — only the module path moves to your shape — so the rest of your `update` and `subscriptions` need no edits.

A `Web` app follows the same rule with its own shape's modules:

```ipe ipe:error
-- accepted: the Web shape's own Cmd / Sub
module Main exposing (main)

import Ipe.Tea.Web as Web
import Ipe.Tea.Web.Cmd as Cmd
import Ipe.Tea.Web.Sub as Sub

main =
    Web.tea { init = init, update = update, view = view, subscriptions = subs }
```

## Why this happens

The three shapes render and drive through different runtime backends, and their `Cmd` / `Sub` surfaces are not interchangeable: a `Cmd` that means one thing in a browser session has no denotation in a terminal frame loop. Rather than let a cross-shape import through and emit Rust that fails to build — or, worse, links against the wrong backend — the compiler proves the app's shape from its entry kernel and fails closed the moment a `Cmd` / `Sub` reference from a different shape appears.

The plain `Ipe.Cmd` / `Ipe.Sub` modules are **not** importable: `Cmd` and `Sub` are always reached through a shape. This keeps every program's shape explicit and unambiguous, with no shape-agnostic back door that the gate would have to second-guess.

## Two shapes in one module

A module builds at most one app, so it imports at most one shape. A second shape import is rejected at that import, naming the first:

```ipe ipe:error
module Main exposing (main)

import Ipe.Tea.Web
import Ipe.Tea.Tui

main =
    1
```

Keep the one shape this module builds, and import that shape's `Cmd` / `Sub` only.
