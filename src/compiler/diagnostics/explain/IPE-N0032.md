# IPE-N0032: type alias expansion too deep or too large

A `type alias` chain or diamond caused the compiler to exceed its expansion budget before it could produce a fully-expanded type. Two independent limits protect against two different pathological shapes:

- **Depth limit (128):** a long straight chain of aliases (`type alias A1 = A0`, `type alias A2 = A1`, …) stacks one native frame per expansion and can overflow the thread stack. The cap sits with comfortable headroom below where a debug build's thread stack would actually overflow, so the error fires deterministically in every build profile.
- **Node limit (100 000):** a diamond of aliases where each level doubles the work (`type alias A1 = (A0, A0)`, `type alias A2 = (A1, A1)`, …) is acyclic so the cycle guard never fires, but the total number of nodes produced grows exponentially. The node budget bounds that regardless of tree shape.

When the compiler hits either limit it rejects the program here rather than crashing or hanging.

A well-typed program never needs alias chains this deep or this wide. If you are hitting this limit legitimately, the fix is to break the chain into smaller named types. A chain of 140 aliases trips the depth limit the moment something expands `A139`:

Introduce a concrete named type at an intermediate point instead of stacking the whole chain:

```ipe
type alias SmallChain = Int
type alias LargerChain = ( SmallChain, SmallChain )
```


A direct self-referential alias is also rejected, but with a different error (the alias is cyclic and the path-based cycle guard fires first, never this page's code):

```ipe ipe:skip a self-referential alias is refused with the cycle guard's own code, never this page's; an explain page's error fence can only assert its own page's code
type alias Loop = Loop
```
