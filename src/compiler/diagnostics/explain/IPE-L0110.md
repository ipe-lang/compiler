# IPE-L0110: partial or over-application not supported yet

You partially applied a *first-class function value* — a function held
in a local binding, returned from another call, or written as a lambda —
producing a new function that still waits for more arguments. Ipe
understands what you mean, but this version of the Rust backend cannot
lower an under-applied call on a function *value*: doing so would need to
capture the closure and supply its remaining arguments later, a mechanism
the backend has not reached yet.

Partial application of a **named** top-level function already works — the
compiler eta-expands it (`add 2` becomes `\n -> add 2 n`). The limit is
specifically the *value* path: once a function is bound to a name, stored,
or returned, applying it with fewer arguments than it takes hits this
error.

The same limit appears in one over-application shape. When a function
declares fewer parameters than its type has arrows (`f a = \b -> \c -> …`
with type `Int -> Int -> Int -> Int`), `f` returns a closure. Applying
`f` with *some but not all* of that closure's arguments — `f 1 2`, which
saturates `f`'s one parameter and then under-applies the returned
two-argument closure — leaves the value partially applied, so it fails
the same way. Passing every argument at once (`f 1 2 3`) lowers fine.

The compiler refuses rather than emit a call it cannot lower soundly:
silently dropping arguments would produce Rust that fails to compile or
computes the wrong answer. Until first-class-value partial application
lands, give the value every argument it needs at one call site — or wrap
the gap in an explicit lambda so the captured value is applied in full.

`[feature: partial-over-application]`

Partial application of a function value — `g` is a returned closure that
takes two arguments, applied with one:

```ipe ipe:skip the under-application shape IPE-L0110 flags; shown without running the checker
f : Int -> Int -> Int -> Int
f a = \b -> \c -> a + b + c

main =
    let g = f 1 in
    let h = g 2 in        -- g is a value; this under-applies it
    println (String.fromInt (h 3))
```

Apply the returned closure in full at one site:

```ipe ipe:skip the full-application fix; shown without running the checker
f : Int -> Int -> Int -> Int
f a = \b -> \c -> a + b + c

main =
    let g = f 1 in
    println (String.fromInt (g 2 3))   -- both arguments at once
```

Over-application that under-saturates the returned closure — `f 1 2`
leaves the two-argument result waiting for one more:

```ipe
f : Int -> Int -> Int -> Int
f a = \b -> \c -> a + b + c

oops : Int -> Int
oops = \n -> let h = f 1 2 in h n     -- f 1 2 under-applies the closure
```

Pass every argument the closure needs at the same call site:

```ipe
f : Int -> Int -> Int -> Int
f a = \b -> \c -> a + b + c

ok : Int
ok = f 1 2 3                          -- surplus saturates the closure exactly
```

This is a current limitation of the Ipe Rust compiler, not a problem
with your code. If first-class-value partial application is important to
your project, please tell us at
https://github.com/ipe-lang/compiler/issues.
