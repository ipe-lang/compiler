# IPE-N0044: the CustomElement.fromFile constructor is malformed at its use site

Ipê talks to a JavaScript widget through one typed door: the reserved `CustomElement down up` type. You name the widget's hook file with the reserved `CustomElement.fromFile` constructor, and you use the resulting handle in a view with `CustomElement.node`.

The `CustomElement.fromFile` constructor is deliberately narrow. It is legal in exactly ONE place — as the whole body of a binding you have annotated `CustomElement down up` — and it takes exactly ONE thing: a single string literal naming the widget-hook JavaScript file inside your project. That is the same discipline the standard library's `Kernel.kernel "…"` aliases use: the compiler must be able to read the file path at build time, so it must be spelled out as a literal.

This is the one accepted shape:

```ipe ipe:skip the widget-hook file must actually exist inside the project root (the build stage that owns the root verifies this); this isolated single-module checker never creates a `js/` directory, so even this well-shaped constructor is refused with IPE-N0044 for a missing file, never accepted
module Main exposing (main)

import Ipe.Ffi.Js.CustomElement as CustomElement

type alias EditorState =
    { text : String }

type EditorEvent
    = TextChanged String

type Msg
    = Edited EditorEvent

codeEditor : CustomElement EditorState EditorEvent
codeEditor =
    CustomElement.fromFile "js/code-editor.js"

stateOf : EditorState -> EditorState
stateOf state =
    state

view : EditorState -> Element Msg
view model =
    CustomElement.node codeEditor (stateOf model) Edited
```

The string is not a type parameter — the two parameters `down` and `up` are the *seal*, the shapes that cross the Ipê↔JS boundary. The JavaScript file is a plain value argument. And because the compiler resolves that path at build time, it must point at a file that actually exists, inside your project — a `..` that climbs out of the project root, or an absolute path, is refused (a build reading an arbitrary file outside the project is a path-traversal footgun, so the safe outcome is the only one allowed).

Each of these trips the gate — a non-literal argument (the path cannot be read at build time), and an absolute (rooted) path:

```ipe ipe:error
module Main exposing (main)

import Ipe.Ffi.Js.CustomElement as CustomElement

type alias EditorState =
    { text : String }

type EditorEvent
    = TextChanged String

whichFile : String
whichFile =
    "js/editor.js"

codeEditor : CustomElement EditorState EditorEvent
codeEditor =
    CustomElement.fromFile whichFile
```

```ipe ipe:error
module Main exposing (main)

import Ipe.Ffi.Js.CustomElement as CustomElement

type alias EditorState =
    { text : String }

type EditorEvent
    = TextChanged String

codeEditor : CustomElement EditorState EditorEvent
codeEditor =
    CustomElement.fromFile "/etc/secrets/editor.js"
```

To fix it, give the binding a `CustomElement down up` annotation, make its whole body `CustomElement.fromFile "<js-path>"` with a single string literal, keep the path inside your project (no `..`, no leading `/`), and make sure the file is really there.
