# IPE-L0141: a Task effect was discarded in a non-Task context, escaping the Task effect discipline

In Ipê an effect — printing a line, reading a file, sleeping — is not something
that *happens* when you write it. It is a **value**: a `Task`. Writing
`Io.println "hi"` does not print anything on its own; it builds a `Task` that
*will* print when it is run. Nothing runs until you hand the `Task` to
`Task.run`, or return it from a function whose type is itself a `Task` (so its
caller runs it in turn).

That is the whole point of the `Task` discipline: you can always tell, from a
function's type alone, whether it can perform effects. A function typed
`String -> String` is pure — give it a string, get a string, no I/O, ever.

## What went wrong

You discarded a `Task` as a bare line inside a `do` block, in a function that
does **not** return a `Task`. A bare line with no `<-` binds nothing — it
desugars to exactly the `let _ = <task>` effect discard above:

```ipe ipe:error
import Ipe.Io as Io

greet : String -> String        -- says: pure, no effects
greet name =
    do
        Io.println ("hello " ++ name)   -- but this is a Task…
        name
```

There is no enclosing `Task` here to fold that effect into. To make the print
actually happen, the compiler would have to run it on the spot — through a
hidden `Task.run` buried inside a function the type promises is pure. Then a
value of type `String -> String` would secretly print to your terminal. Every
guarantee the `Task` type gives you would be a lie.

So this is rejected. An effect escapes into pure-looking code exactly once, and
then you can never trust a type again — the compiler refuses the first step.

## Where it is fine

Sequencing effects inside a `Task`-returning function is fine — use a `do`
block or `|> Task.andThen` so each effect is explicitly chained, not silently
discarded:

```ipe
import Ipe.Io as Io

main : Task Error ()
main =
    do
        Io.println "step one"
        Io.println "step two"
```

Here nothing runs until `main` runs. Both lines print, in order, lawfully.
(See `ipe doc IPE-P0064` for why `let _ = effect` is not the supported form
even inside a `Task` — `do` or `|> Task.andThen` is.)

## How to fix it

**Make the function a `Task`.** If it genuinely needs to do I/O, say so in its
type, and let its result be the sequenced effects:

```ipe
import Ipe.Io as Io
import Ipe.Task as Task

greet : String -> Task Error String
greet name =
    Io.println ("hello " ++ name)
        |> Task.andThen (\_ -> Task.succeed name)
```

Its caller now runs the returned `Task`, so the print happens under the
caller's control — in the open, not smuggled inside a pure signature.

**Run it explicitly.** If you are at the top level and just want the effect,
sequence it with `|> Task.andThen`:

```ipe ipe:skip a comment-only placeholder, not executable code
-- run one effect then another; see do-block or Task.andThen for sequencing
```

**You are only debugging.** To peek at a value mid-expression without turning
the function into a `Task`, use `Debug.log`. It prints to stderr and returns
the value unchanged, so it fits anywhere — and `ipe release` rejects it
(IPE-L0140), so it can never ship by accident:

```ipe
import Ipe.Debug as Debug

greet name =
    Debug.log "greeting" ("hello " ++ name)
```

## Glossary

- **effect** — an observable interaction with the outside world (printing,
  reading, sleeping). From Latin *efficere*, "to bring about".
- **Task** — Ipê's type for a *described, not-yet-run* effect. Holding a `Task`
  is holding a plan; running it carries the plan out.
- **`Task.run`** — the one place an effect actually happens. Everything else
  only builds and combines `Task`s.
- **discipline** — a rule the language keeps everywhere, so a property (here:
  "the type tells you whether a function does I/O") holds without exception.
  From Latin *disciplina*, "instruction, training".
- **pure** — a function whose output depends only on its input and which
  performs no effect. `String -> String` is pure; `String -> Task e String` is
  not.
