# IPE-T0019: each alternative of an or-pattern must bind the same variables

An **or-pattern** lets one `case` arm match several shapes, separated by `|`:

```ipe
type Direction
    = Up
    | Down
    | Left
    | Right

describe : Direction -> String
describe d =
    case d of
        Up | Down    -> "vertical"
        Left | Right -> "horizontal"
```

When the arm binds a variable, the body reads that variable *without knowing
which alternative actually matched*. So every alternative must bind the **same
set of variable names**, each at the **same type** — the rule Rust, OCaml, and
F# all share. That is exactly what makes the body well-typed regardless of which
alternative fired:

```ipe
import Ipe.Math as Math

type Shape
    = Circle Float
    | Square Float

area : Shape -> Float
area shape =
    case shape of
        -- both alternatives bind `r`, so `area r` is well-typed either way
        Circle r | Square r -> Math.pi * r * r
```

## Why this is an error

If one alternative bound a name the other did not, the body could read a
variable that does not exist on the path the value actually took — an unbound
name at best, an unsound read at worst. Requiring one common binder set makes
that state unrepresentable: the body is type-checked **once**, against a single
environment that every alternative agrees on.

Here `r` is bound by the left alternative but not the right, so the arm is
rejected and the message names `r`:

```ipe ipe:error
-- error: `r` is bound by `Circle r` but not by `Nothing`
badArea : Shape -> Float
badArea shape =
    case shape of
        Circle r | Nothing -> r
```

## How to fix it

Bind the same names on every alternative, or bind none:

```ipe
type Shape
    = Circle Float
    | Square Float
    | Triangle Float

-- ok: no binding on either side — the alternatives just select a shape
label : Shape -> String
label shape =
    case shape of
        Circle _ | Square _ -> "round-ish"
        Triangle _          -> "pointy"
```

Wildcards (`_`) and literals (`0`, `"hi"`, `Up`) bind nothing, so they impose no
obligation: `_ | Nothing`, `0 | 1`, and `Up | Down` are all fine. A same-named
binder that appears on every alternative but at **different types** is a related
error, reported as a type mismatch (IPE-T0001) against the or-pattern.
