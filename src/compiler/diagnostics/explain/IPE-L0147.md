# IPE-L0147: `CustomElement.node` is browser-only and cannot be used outside a Web/WebView shape

`CustomElement.node` mounts a **server-driven custom element** — a browser custom
element (a `<my-editor>`-style tag) that you hand a piece of *down* state and a
handler for the *up* events it sends back. It is the seam between your Ipê view
and a JavaScript-defined web component: the down state is serialised out to the
element, and each up event the element emits is decoded back into a message for
your `update`.

That decode is the catch. The up-event payload rides the **seal codec**, the
fail-closed serialisation layer that exists only in a **browser build**. The
`Web` and `WebView` shapes turn it on (they force the runtime's `json` feature);
the `Terminal` and `Program` shapes do not. Outside a browser shape a
`CustomElement.node` node would have **no transport for its handler** — an inert
element wired to nothing, a widget with no seam. That is rejected here, at
compile time, rather than emitting Rust that would fail to build after
`ipe dev build` already reported success.

```ipe ipe:error
-- rejected: `CustomElement.node` under `Tui.tea` (no browser custom-element seam)
module Main exposing (main)

import Ipe.Tea.Tui as Tui
import Ipe.Ui.Cells exposing (Cells)
import Ipe.Ffi.Js.CustomElement as CustomElement

editor : CustomElement String String
editor = CustomElement.fromFile "js/editor.js"

view : Model -> Cells Msg
view model =
    CustomElement.node editor model.state FromWidget

main =
    Tui.tea { init = init, update = update, view = view, subscriptions = subs }
```

## How to fix

**Use `CustomElement.node` only under a browser shape.** A `Web.tea` (or
`WebView.app`) program has the custom-element runtime and the seal codec, so the
widget's up-events decode into your messages:

```ipe ipe:skip
-- accepted: `CustomElement.node` inside a `Web.tea` view
module Main exposing (main)

import Ipe.Tea.Web as Web
import Ipe.Ui exposing (Element)
import Ipe.Ffi.Js.CustomElement as CustomElement

editor : CustomElement String String
editor = CustomElement.fromFile "js/editor.js"

view : Model -> Element Msg
view model =
    CustomElement.node editor model.state FromWidget

main =
    Web.tea { init = init, update = update, view = view, subscriptions = subs }
```

**If you need this in a terminal app**, build the view from the native `Ipe.Ui`
elements the terminal backend understands — `Ui.text`, `Ui.column`, and the
`Ipe.Input` builders — instead of a browser custom element:

```ipe ipe:skip
-- accepted in every shape: native Ipe.Ui instead of a browser widget
view : Model -> Element Msg
view model =
    Ui.column []
        [ Ui.text "editor:"
        , Ui.text model.state
        ]
```

## Why this happens

The app shapes share one `Element` view type, but each shape can only render the
primitives its runtime backend understands. `CustomElement.node` is a
browser-backend primitive: it lowers to a custom-element node whose up-event
handler is decoded through the seal codec. That codec is compiled in only when
the browser shapes force the runtime's `json` feature — a `Terminal` or `Program`
build never does. The compiler proves the shape from the app entry point
(`Web.tea` / `WebView.app` versus `Tui.tea` / `Cli.tea`) and fails closed the
moment a browser-only node appears in a non-browser build, so an inadmissible
widget is a typed refusal rather than a dead node or a downstream `cargo build`
failure.
