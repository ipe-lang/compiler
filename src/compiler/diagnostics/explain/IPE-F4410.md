# IPE-F4410: no isolation jail can be established for compiling an untrusted crate

You asked me to bind a Rust crate (`ipe add <crate>`), and I refused
because I could not build a safety cage — an *isolation jail* — around
the work. Rather than run the crate's code with your full privileges, I
stopped.

Binding a crate is what makes this Ipê program possible:

```ipe ipe:skip
import Rust.Semver as Semver

main =
    println (Semver.parse "1.2.3")
```

The `Rust.Semver` module only exists after `ipe add semver` has
inspected and compiled the `semver` crate — and that compile step is
where the danger lives.

## Why binding a crate runs its code

`ipe add` does not merely *read* a crate. To learn the crate's public
surface I must compile it, and compiling Rust can execute code the
crate's author wrote:

- a `build.rs` build script runs as an ordinary program;
- procedural macros compile and then *execute* during expansion;
- both are true for every transitive dependency too.

So `ipe add` is, in effect, "download a program from the internet and
run it." That is fine when it happens inside a jail: a sandbox with no
network, a read-only view of your system, a scrubbed environment, and
hard resource limits. It is not fine on the bare host.

Note what is *not* affected: building a project that already carries
its binding cache never re-runs the crate's code —

```ipe ipe:skip
-- a teammate cloning the repo and running `ipe dev build` compiles this
-- against the cached bindings; the foreign crate's build scripts do
-- NOT run again on their machine:
version = Semver.parse "1.2.3"
```

only an explicit `ipe add` / `ipe install` re-inspects, and only
inside the jail.

## What I looked for

On Linux I use `bwrap` (bubblewrap) as the primary jail. If it is
missing I can fall back to `unshare` — but only when I can *prove*,
from inside the child process and before any untrusted code runs, that
every namespace I asked for actually took effect (on some hosts
`unshare` partially fails while still reporting success). If neither
tool is present, or the fallback cannot prove its isolation, you get
this refusal.

## What to do

- Install bubblewrap (`bwrap`) — on most distributions it is the
  package `bubblewrap`. This is the recommended fix.
- Or enable unprivileged user namespaces so the `unshare` fallback can
  prove itself (`sysctl kernel.unprivileged_userns_clone=1` on hosts
  that gate it).
- As a last resort, `IPE_FFI_ALLOW_UNSANDBOXED=1` overrides the
  refusal. I will print a warning first, because it means the crate's
  build scripts and macros run with your full network, filesystem, and
  environment. Never set it in CI.

Once a jail is available, the same command succeeds and the module
appears:

```ipe ipe:skip
-- after a successful `ipe add semver`:
import Rust.Semver as Semver

bump : String -> String
bump v =
    Semver.toStringFromVersion (Semver.parse v)
```

The jail also refuses when its process cap would count more than the
crate's own build: on Linux before 5.14 the kernel counts every
process you own, and as root it counts none. Run `ipe add` as an
unprivileged user on Linux 5.14 or later with unprivileged user
namespaces enabled.

## Glossary

- **jail / sandbox** — a restricted environment a process runs in, so
  it cannot touch the network, your files, or your secrets. "Jail" is
  the old BSD word; "sandbox" the modern one — same idea.
- **namespace** — the Linux kernel feature that gives a process its
  own private view of one resource (the network, process ids, mounts).
  From Latin *spatium*, "space": a separate space of names.
- **`build.rs` / proc-macro** — the two places Rust lets a crate run
  arbitrary code at *compile* time rather than run time.
