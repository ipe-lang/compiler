# IPE-L0135: a non-Clone value (a Task/Cmd/Sub effect or a payload carrying one) is used more than once

A binding whose type is not `Clone` — a `Task` / `Cmd` / `Sub` effect value,
bare or held inside a `Maybe` / `Result` / tuple / record / user-union payload —
was used more than once in a value-CONSUMING position, and the compiler could
not prove the value safe to duplicate.

A `Task` / `Cmd` / `Sub` lowers to an opaque boxed future
(`Pin<Box<dyn Future + Send>>`), which never implements `Clone`. A generic user
union such as `type Wrap a = Wrap a` derives `Clone where T: Clone`, so
instantiating `T` to one of these effect carriers makes that `Clone` bound
unsatisfiable. Reusing the binding a second time in a consuming position would
move an already-moved value, which `cargo` rejects as E0382 (or E0277 on the
missing `Clone`). Rather than emit Rust that fails to build after `ipe dev build`
already reported success, the compiler fails closed here.

```ipe
type Wrap a =
    Wrap a


unwrap : Wrap a -> a
unwrap w =
    case w of
        Wrap x ->
            x


-- before (IPE-L0135 — `w` is consumed twice; `Wrap (Task Error Int)` is not Clone)
pair : Wrap (Task Error Int) -> ( Task Error Int, Task Error Int )
pair w =
    ( unwrap w, unwrap w )
```

## How to fix

**Use the value once.** A `Task` is meant to be run or sequenced through a
single continuation; extract it once and thread the result:

```ipe ipe:skip
-- after (`w` is consumed once; the effect flows through one continuation)
runOnce : Wrap (Task Error Int) -> Task Error ()
runOnce w =
    case w of
        Wrap task ->
            Task.andThen
                (\n -> Io.println (String.fromInt n))
                task
```

**Re-construct the effect for each independent consumer** when the two uses are
genuinely independent — build a fresh `Task` at each site rather than sharing
one binding:

```ipe
-- after (two independent effects, each used once)
both : ( Task Error Int, Task Error Int )
both =
    ( Task.succeed 1, Task.succeed 2 )
```

**Read the fields you need before the consuming use.** A field read such as
`w.tag` borrows the record, which is fine while the record is still owned. Once
an earlier argument has moved the whole record (`consume w`), the field is gone
too, so a read evaluated after that move is rejected. Bind the field with `let`
first, then consume the record:

```ipe ipe:skip
-- before (IPE-L0135 — `consume w` moves `w` before `w.tag` is read)
run w =
    both (consume w) w.tag

-- after (the field is read while `w` is still owned)
run w =
    let
        t =
            w.tag
    in
    both (consume w) t
```

The arguments of a built-in (kernel) call are evaluated in an order the
compiler chooses, so a move of a record and a read of one of its fields in two
arguments of the same built-in call are rejected in either written order — the
`let` binding is the fix there as well.

## Why this happens

An effect value (`Task` / `Cmd` / `Sub`) carries a boxed future, the only sound
Rust representation for a deferred computation. A boxed future is not `Clone`, so
the backend cannot insert a duplicating `.clone()` for a non-linear use. A
`Decoder` is different — it carries an `Arc<dyn Fn>` with an unconditional
`Clone` — so a `Decoder` reused across sites is accepted.

## Types affected

- A bare `Task` / `Cmd` / `Sub` value reused as a value more than once.
- The same effect held inside a `Maybe` / `Result` / tuple / record / user-union
  payload — the whole value inherits the effect's non-`Clone`-ness.
- A field of such a record read after the record itself was consumed.
