# IPE-N0040: a decoder-pipeline combinator is hand-nested instead of threaded with |>

The decoder-pipeline combinators — `Db.Decode.required` / `optional`, and
`Json.Decode.Pipeline`'s `required` / `optional` / `requiredAt` / `custom` —
build a record decoder one field at a time. Each combinator takes the *decoder
so far* as its LAST argument and adds one more field to it. Because the
accumulator comes last, the natural way to write a pipeline is the forward pipe
`|>`, which feeds each stage's result into the next:

```ipe
import Ipe.Db.Decode


type alias User =
    { name : String, email : String }


userDecoder : Db.Decode.Decoder User
userDecoder =
    Db.Decode.succeed User
        |> Db.Decode.required "name" (Db.Decode.string "name")
        |> Db.Decode.required "email" (Db.Decode.string "email")
```

Each column primitive (`Db.Decode.string`, `Db.Decode.int`, …) takes the
column name itself and returns a one-column `Decoder`; `required`'s own name
argument is kept for parity with `Json.Decode.Pipeline.required` but plays no
role in which column is read.

Read top to bottom, the fields are applied to `User` in the order they appear:
`name` first, then `email`. That matches the constructor `User name email`.

## What went wrong

The same combinators can be *hand-nested* by passing the accumulator as an
explicit parenthesised argument instead of piping it. But nesting reverses the
order: the INNERMOST call is the one that reaches the constructor first.

```ipe ipe:error
-- rejected: the innermost `required` binds to `User` FIRST, so this
-- applies `email` before `name` — the reverse of how it reads
import Ipe.Db.Decode


type alias User =
    { name : String, email : String }


userDecoder : Db.Decode.Decoder User
userDecoder =
    Db.Decode.required "name" (Db.Decode.string "name")
        (Db.Decode.required "email" (Db.Decode.string "email")
            (Db.Decode.succeed User))
```

When `name` and `email` have the SAME type (`String`), the type checker sees
nothing wrong — both orders type-check. So a `User` you meant to build as
`User name email` is silently built as `User email name`. The bug only shows up
at run time, as swapped data. To make invalid states unrepresentable, the
compiler refuses the hand-nested form outright.

This is caught even when the inner decoder is reached through a binding, so
splitting the nesting across a `let` or a top-level value does not hide it:

```ipe ipe:error
-- rejected: `rest` is still the reverse-nested accumulator, just named
import Ipe.Db.Decode


type alias User =
    { name : String, email : String }


userDecoder : Db.Decode.Decoder User
userDecoder =
    let
        rest =
            Db.Decode.required "email" (Db.Decode.string "email")
                (Db.Decode.succeed User)
    in
    Db.Decode.required "name" (Db.Decode.string "name") rest
```

## How to fix

Thread the combinators with `|>` so they read in the same order the fields bind:

```ipe
import Ipe.Db.Decode


type alias User =
    { name : String, email : String }


userDecoder : Db.Decode.Decoder User
userDecoder =
    Db.Decode.succeed User
        |> Db.Decode.required "name" (Db.Decode.string "name")
        |> Db.Decode.required "email" (Db.Decode.string "email")
```

The `|>` form is not just tidier — it is the only form whose written order
matches its binding order, so it cannot silently swap two same-typed fields.

## Glossary

- **combinator** — a small building-block function you combine with others to
  build a larger value; here, each one adds one field to a growing decoder.
- **accumulator** — the running result carried through a pipeline. For these
  decoders it is the *decoder built so far*, threaded as the last argument.
- **pipe (`|>`)** — the forward-pipe operator: `x |> f` means `f x`, feeding the
  left value into the function on the right. Chaining `|>` reads top to bottom.
- **decoder** — a value that describes how to turn stored or foreign data (a
  database row, a JSON object) into a typed Ipê value.
